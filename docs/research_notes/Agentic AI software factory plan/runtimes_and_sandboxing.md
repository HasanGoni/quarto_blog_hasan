# Coding-agent runtimes and sandboxing/permission options for a single-machine software factory

Research date: 2026-10-17. All code.claude.com and docs.langchain.com pages below were fetched on 2026-10-17 and are "live" docs without a visible page date. Version gates are quoted where the page states them. The local `claude` binary on the target box reports 2.1.302. Anything marked UNVERIFIED could not be confirmed from a primary source.

## 1. Claude Agent SDK and Claude Code headless: permissions, hooks, settings scopes, sandbox, and how to make a path unwritable or unreadable

### Takeaway
Claude Code gives three layers: (a) permission rules and modes (a policy gate on tool calls, deny always wins), (b) hooks (code-based gate, runs before everything), and (c) an OS-level Bash sandbox (bubblewrap on Linux). Only (c) constrains arbitrary subprocesses, and it covers Bash only, not the built-in Read/Edit tools, MCP servers or hooks. A hard "agent can never write directory X / read dataset Y" guarantee needs deny rules plus the sandbox plus (ideally) an outer boundary (separate OS user, container, or VM), because the docs themselves say permission rules are not a sandbox.

### Cited Findings

**Submitting tasks and collecting results**
- `claude -p "..."` runs non-interactively. Exit code 0 on success, non-zero on failure. `--output-format` is `text` (default), `json`, or `stream-json`. `json` returns result, session ID and metadata; `--json-schema` puts schema-conformant output in `structured_output`. — [Run Claude Code programmatically](https://code.claude.com/docs/en/headless)
- `--output-format json` includes `total_cost_usd` and a per-model cost breakdown. `--resume <session_id>` / `--continue` continue a session. Final line of `stream-json` is a `result` message. Denials appear as `permission_denied` system messages and in `permission_denials` on the final result. — [headless](https://code.claude.com/docs/en/headless)
- `--bare` skips auto-discovery of hooks, skills, plugins, MCP servers, auto memory and CLAUDE.md; docs say it "is the recommended mode for scripted and SDK calls, and will become the default for `-p` in a future release". Bare mode does not read OAuth/keychain; needs `ANTHROPIC_API_KEY` (or Bedrock/Vertex/Foundry creds). Without `--bare`, `-p` runs hooks from a project's `.claude/settings.json` and connects its `.mcp.json` servers even in an untrusted folder and shows no trust dialog. — [headless](https://code.claude.com/docs/en/headless)
- SIGTERM to `claude -p` exits 143 with the turn unfinished and no result recorded; SIGINT or SDK `interrupt()` ends the turn properly. SIGTERM kills the Bash process tree. — [headless](https://code.claude.com/docs/en/headless)
- Piped stdin is capped at 10MB. A `-p` run waits for background work up to a 10-minute idle cap (`CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`). — [headless](https://code.claude.com/docs/en/headless)
- The Agent SDK (Python `claude_agent_sdk`, TypeScript `@anthropic-ai/claude-agent-sdk`) "runs the Claude Code binary" with built-in tools, hooks, subagents, MCP, permissions, sessions. For other languages, run the CLI as a subprocess with `-p --output-format json`. — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)
- Auth/licensing note: "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK. Use the API key authentication methods". SDK use is governed by Anthropic's Commercial Terms. — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)

**Permission modes (exact names)**
- `default` (alias `manual`), `acceptEdits`, `plan`, `auto` (a background classifier model reviews actions), `dontAsk` (auto-denies anything that would prompt), `bypassPermissions`. Set via `defaultMode` in settings or `--permission-mode` / SDK `permissionMode`. — [Configure permissions](https://code.claude.com/docs/en/permissions)
- A run where nothing sets a permission mode takes a built-in starting mode "which can be `auto`", so pass the mode explicitly. The TypeScript SDK note: before SDK v0.3.286 omitting `permissionMode` equalled `default`. — [headless](https://code.claude.com/docs/en/headless); [SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions)
- `bypassPermissions` skips prompts "including for writes to protected paths such as `.git` and `.claude`"; docs: "Only use this mode in isolated environments like containers or VMs". On Linux/macOS Claude Code refuses to start with it as root outside a recognized sandbox. `permissions.disableBypassPermissionsMode` / `permissions.disableAutoMode` set to `"disable"` turn those modes off from any settings file. — [permissions](https://code.claude.com/docs/en/permissions); [sandbox environments](https://code.claude.com/docs/en/sandbox-environments)
- For a locked-down headless agent: `allowedTools` plus `permissionMode: "dontAsk"` (example in SDK docs uses `["Read","Glob","Grep"]`). — [SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions)
- `--permission-prompts none` (v2.1.259+) denies anything that would prompt and tells Claude not to retry; the SDK TypeScript equivalent is `permissionPrompts: 'none'`. — [headless](https://code.claude.com/docs/en/headless)
- Subagent inheritance: a subagent runs in `bypassPermissions` only when the parent does (v2.1.267+); subagents may have "less constrained behavior". — [SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions)

**Rule syntax and evaluation order**
- Rules are evaluated deny, then ask, then allow; first match wins; "An allow rule can't carve an exception out of a deny rule." Deny at any scope beats allow at any other scope; managed settings are highest and cannot be overridden by CLI args (`--allowedTools` cannot override a managed deny). — [permissions](https://code.claude.com/docs/en/permissions)
- SDK evaluation order: hooks, deny rules, ask rules, permission mode, allow rules, `canUseTool` callback. Deny rules block "even in `bypassPermissions` mode". A hook `allow` does not skip deny/ask rules. — [SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions); [permissions](https://code.claude.com/docs/en/permissions)
- A bare tool name in deny (e.g. `Bash`, or `disallowed_tools=["Bash"]`) removes the tool from the model's context entirely. `disallowed_tools=["*"]` removes all tools. — [SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions)
- GOTCHA: `allowed_tools` only pre-approves; "`allowed_tools` does not constrain `bypassPermissions`". `allowed_tools=["Read"]` with `bypassPermissions` still approves Bash/Write/Edit. Use `disallowed_tools` to block. — [SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions)
- GOTCHA: auto-approved tool calls never reach `canUseTool`; for checks on every call, use a `PreToolUse` hook. — [SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions)
- Auto mode drops a bare `Bash` allow entry (broad allow rule) from `--allowedTools`. — [headless](https://code.claude.com/docs/en/headless)

**Path-rule semantics for protecting directories (Read/Edit deny rules)**
- Path rules use gitignore pattern syntax with four anchors: `//path` = absolute from filesystem root (e.g. `Edit(//secrets/**)`), `~/path` = home, `/path` = relative to the settings source (NOT filesystem root; `Read(/secrets/**)` in user settings means `~/.claude/secrets/**`), `./path` or bare = relative to cwd. — [permissions: Read and Edit](https://code.claude.com/docs/en/permissions)
- `Edit(path)` rules govern all built-in write tools incl. Write and NotebookEdit; a `Write(path)` rule is "never matched by the file permission checks" (warned at startup, v2.1.210+). A `Read` deny also blocks Edit/Write on the same path (v2.1.208+ edits, v2.1.228+ writes); NotebookEdit is not covered by Read deny, so add an `Edit` deny. — [permissions](https://code.claude.com/docs/en/permissions); [SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions)
- Deny rules apply when either the requested path or its symlink target matches (a symlink pointing at a denied file is denied). A deny written through a symlinked directory with `//`, `~/` or `/` also applies at the real location (v2.1.268+). — [permissions: Symlinks](https://code.claude.com/docs/en/permissions)
- KEY LIMIT (quoted warning): "Read and Edit deny rules apply to Claude's built-in file tools, to file commands Claude Code recognizes in Bash, such as `cat`, `head`, `tail`, `sed`, and `tee`, and to the targets of Bash redirections... They don't apply to a command that reads files without naming them, such as `grep -r pattern .`... or to arbitrary subprocesses that read or write files indirectly, like a Python or Node script that opens files itself. For OS-level enforcement that blocks all processes from accessing a path, enable the sandbox." — [permissions](https://code.claude.com/docs/en/permissions)
- Bash argument-pattern rules are described as "fragile" (e.g. `Bash(curl http://github.com/ *)` is bypassed by option reordering, other protocols, redirects, variables). Bash commands are parsed to an AST for permission matching; the secure-deployment guide calls this "a permission gate, not a sandbox". — [permissions](https://code.claude.com/docs/en/permissions); [secure deployment](https://code.claude.com/docs/en/agent-sdk/secure-deployment)

**Settings scopes**
- Locations: `~/.claude/settings.json` (user), `.claude/settings.json` (project, committable), `.claude/settings.local.json` (project, gitignored), managed policy settings (org, admin-controlled), plugin `hooks/hooks.json`, skill and subagent frontmatter. — [hooks reference](https://code.claude.com/docs/en/hooks)
- Managed settings cannot be overridden by user/project/CLI except a few security-sensitive keys; `allowManagedPermissionRulesOnly` makes managed settings the only source of permission rules. — [permissions: Managed settings](https://code.claude.com/docs/en/permissions)
- SDK: project `.claude/settings.json` rules are read when the `project` setting source is enabled, which it is for default `query()` options; if you set `setting_sources`/`settingSources` explicitly include `"project"` for them to apply. — [SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions)
- `--settings '<json-or-file>'` injects settings; the docs use `--settings '{"disableAllHooks": true}'` to turn hooks off for a run and note project settings can override user-level settings. — [permissions](https://code.claude.com/docs/en/permissions)
- UNVERIFIED for factory use: whether managed settings can be deployed on a Linux box without root. The docs describe delivery via MDM / server-managed settings; the filesystem path for the Linux managed file is on the managed-settings page, which I did not fetch (it will normally be a root-owned system path such as `/etc/...`; unconfirmed here). Without sudo, the practical equivalent is passing `--settings` from the orchestrator, but a `--settings` value is not shown to outrank repo-level files except in the sandbox "admin-required" case below.

**Hooks (PreToolUse)**
- Events include `PreToolUse`, `PermissionRequest`, `PermissionDenied`, `PostToolUse`, `PostToolUseFailure`, `UserPromptSubmit`, `SubagentStart/Stop`, `Stop`, `SessionStart/End`, `WorktreeCreate`, `WorktreeRemove`, `FileChanged`, `ConfigChange`, `CwdChanged`, `PreCompact`, and others (about 33 listed). Hook types: `command`, `http`, `mcp_tool`, `prompt`, `agent` (agent hooks marked experimental). — [hooks reference](https://code.claude.com/docs/en/hooks)
- PreToolUse input JSON has `hook_event_name`, `tool_name`, `tool_input`, `tool_use_id`. Output: `hookSpecificOutput.permissionDecision` of `allow|deny|ask|defer` plus `permissionDecisionReason`. Exit code 2 blocks the call (stderr is the reason) even if JSON says allow. — [hooks reference](https://code.claude.com/docs/en/hooks)
- Failure semantics: other non-zero exit codes and hook timeouts are NON-blocking by default; `"onFailure": "block"` on a command/http hook changes this (needs v2.1.295+). So a crashing guard hook fails open unless you set this. — [hooks reference](https://code.claude.com/docs/en/hooks)
- Matcher: exact tool names or `A|B` lists; any other character makes it a JS regex (`mcp__memory__.*`). `if` field uses permission-rule syntax such as `"Bash(git *)"`. — [hooks reference](https://code.claude.com/docs/en/hooks)
- Hooks vs rules precedence: PreToolUse decisions "don't bypass permission rules"; deny/ask rules still apply after a hook `allow`. "A hook that exits with code 2 stops the tool call before permission rules are evaluated", and "a hook deny applies even in `bypassPermissions` mode". — [permissions: Extend permissions with hooks](https://code.claude.com/docs/en/permissions); [SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions)
- Hooks (command hooks) and MCP servers run as ordinary host processes, outside the Bash sandbox. — [sandbox environments](https://code.claude.com/docs/en/sandbox-environments)
- A repo's `.claude/settings.json` hooks run under `-p` without trust prompt unless `--bare` (see above): a ticket-modified repo can therefore add hooks that run on the host. — [headless](https://code.claude.com/docs/en/headless)

**Built-in sandbox (Bash tool) on Linux**
- Mechanism: "The Bash sandbox is a boundary that the operating system enforces around the shell commands Claude runs... applies to Bash, PowerShell, and Monitor commands and the processes they start." Linux/WSL2 use `bubblewrap` and `socat` (network relay to a proxy); ripgrep and a seccomp filter are also listed as dependencies. — [Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Default: writes allowed to cwd, per-user temp dir and `--add-dir`/`permissions.additionalDirectories`; reads allowed across most of the machine "including credential files such as `~/.ssh` and `~/.aws/credentials`" unless denied. Protected paths stay write-denied, with no exemption mechanism short of `filesystem.disabled`. — [Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Settings (under `sandbox`): `enabled`, `failIfUnavailable`, `allowUnsandboxedCommands`, `autoAllowBashIfSandboxed` (default true), `excludedCommands`, `enableWeakerNestedSandbox`, `enableWeakerNetworkIsolation`, `filesystem.allowWrite`, `filesystem.denyWrite`, `filesystem.denyRead`, `filesystem.allowRead`, `filesystem.disabled`, `network.allowedDomains`, `network.allowUnixSockets`, `network.allowAllUnixSockets`, `network.allowLocalBinding`, `network.strictAllowlist`, `network.allowManagedDomainsOnly`, `network.tlsTerminate` (experimental), `allowManagedReadPathsOnly`, `credentials`. — [Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Read-region semantics: narrower path wins in overlaps for allowRead vs denyRead; a `denyRead` inside a wider `allowRead` holds. Example: `"denyRead": ["~/"], "allowRead": ["."]`. Note `.` resolves relative to the settings file's location (a user-scope `.` resolves to `~/.claude`). — [Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Sandbox, permissions rules and `Edit` allow rules are merged into the final sandbox config; `Edit` allow rules grant write access like `allowWrite`. `denyWrite`/`denyRead` "block subprocess access to specific paths". — [Sandboxing: Permission rules](https://code.claude.com/docs/en/sandboxing)
- Escape hatch: Claude can retry a failed command with `dangerouslyDisableSandbox`; disable with `"allowUnsandboxedCommands": false`. Also by default, if bubblewrap or deps are missing "Claude Code runs commands without sandboxing", unless `sandbox.failIfUnavailable` is `true`. Example from docs: `claude --settings '{"sandbox": {"enabled": true, "allowUnsandboxedCommands": false}}'`. — [Sandboxing](https://code.claude.com/docs/en/sandboxing)
- If the unsandboxed retry is disabled via managed settings or `--settings`, the sandbox becomes "admin-required": repository settings that loosen it (including `excludedCommands`, `allowWrite`) are ignored (v2.1.285+). This is the documented way to stop a checked-out repo from loosening the sandbox without root-owned managed files. — [Sandboxing: Repository settings under an admin-required sandbox](https://code.claude.com/docs/en/sandboxing)
- Does NOT cover: Claude's built-in Read/Edit/Write/WebFetch/WebSearch (use permission rules; "A `denyRead` entry doesn't stop the Read tool"), MCP servers, hooks, excluded commands, unsandboxed retries. Subagents inherit the parent sandbox config. — [Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Security limitations (quoted topics): proxy filters by client-supplied hostname without TLS inspection so domain fronting is possible and broad domains like `github.com` can allow exfiltration; `allowUnixSockets` can bypass the sandbox (example `/var/run/docker.sock`); writable `$PATH`/shell-rc directories enable privilege escalation; `enableWeakerNestedSandbox` "considerably weakens security". Same-host kernel, so a kernel vulnerability could theoretically enable escape. — [Sandboxing: Security limitations](https://code.claude.com/docs/en/sandboxing); [secure deployment](https://code.claude.com/docs/en/agent-sdk/secure-deployment)
- Ubuntu 24.04+: default AppArmor policy blocks bubblewrap user namespaces when `kernel.apparmor_restrict_unprivileged_userns` is 1; docs fix is to add an AppArmor profile at `/etc/apparmor.d/bwrap` and reload AppArmor (needs root). — [Sandboxing: Set up Linux and WSL2](https://code.claude.com/docs/en/sandboxing)

**Whole-process isolation (what to do for untrusted code)**
- Docs compare: sandboxed Bash tool (Bash only), sandbox runtime `@anthropic-ai/sandbox-runtime` (whole process incl. file tools, MCP, hooks; "a beta research preview"; config in `~/.srt-settings.json`; launch `npx @anthropic-ai/sandbox-runtime claude`), dev container (Anthropic example has a default-deny iptables firewall), custom container, VM (strongest; recommended for untrusted repos), cloud sessions. — [Choose a sandbox environment](https://code.claude.com/docs/en/sandbox-environments)
- Quote: "Always run `--dangerously-skip-permissions` sessions inside a container, a VM, or the sandbox runtime, so that file tools, MCP servers, and hooks are also inside the boundary." The sandboxed Bash tool alone "is not sufficient for fully unattended runs in either mode" (bypass or auto). Auto mode's classifier "is a per-action control, not an isolation boundary". — [sandbox environments](https://code.claude.com/docs/en/sandbox-environments)
- sandbox-runtime on Linux builds its deny list for nested `.git`/config copies once at launch; later `git init`/`git clone` inside the session are not covered; also write grants should exclude Claude Code config paths, else the session can persist hooks/permissions/MCP servers that run unsandboxed on next launch. — [sandbox environments](https://code.claude.com/docs/en/sandbox-environments)
- Hardened container recipe from the docs: `--cap-drop ALL`, `--security-opt no-new-privileges`, custom seccomp profile, `--read-only`, `--tmpfs /tmp:rw,noexec,nosuid,size=100m`, `--network none` plus a mounted Unix-socket proxy, `--memory`, `--cpus`, `--pids-limit 100`, `--user 1000:1000`, `-v /path/to/code:/workspace:ro`; add `--userns-remap`, `--ipc private`. Avoid mounting `~/.ssh`, `~/.aws`, `~/.config`. — [secure deployment](https://code.claude.com/docs/en/agent-sdk/secure-deployment)
- Isolation strength table in the docs: sandbox runtime "Good", Docker "Setup dependent", gVisor "Excellent (with correct setup)", VMs "Excellent (with correct setup)". gVisor overheads: simple syscalls ~2x slower, file-I/O heavy up to 10-200x slower. — [secure deployment](https://code.claude.com/docs/en/agent-sdk/secure-deployment)
- Credential proxy pattern: keep API keys outside the agent boundary; proxy injects credentials; `ANTHROPIC_BASE_URL` for sampling, `HTTP_PROXY`/`HTTPS_PROXY` for others; Node `fetch()` ignores proxy env vars by default (Node 24+ `NODE_USE_ENV_PROXY=1`). Overlay filesystem suggested to review agent writes before persisting. — [secure deployment](https://code.claude.com/docs/en/agent-sdk/secure-deployment)

### Inferences
- A defensible "cannot touch X" design is layered: (1) outer boundary where X is physically read-only or absent (container with `-v X:/x:ro`, or X owned by another OS user with mode 0444/0555 and the agent running as a different user, or simply not mounted); (2) `permissions.deny` `Edit(//X/**)` and `Read(//sealed/**)` for the built-in tools; (3) `sandbox.filesystem.denyWrite` / `denyRead` with `allowUnsandboxedCommands:false` and `failIfUnavailable:true` for Bash subprocesses; (4) a PreToolUse hook with `onFailure: "block"` as a fail-closed backstop. Layers 2-4 alone are weaker than 1 because the docs say Read/Edit rules do not cover arbitrary subprocesses and hooks fail open by default.
- The sealed held-out labels are best kept out of any filesystem path visible to the agent process at all (evaluator runs as another user or in another container and returns only a score). Deny rules protect against accidents and prompt injection, not a determined model with an exploitable sandbox gap.
- `--bare -p` plus explicit `--settings`, `--allowedTools`, `--disallowedTools`, `--permission-mode dontAsk` is the most reproducible headless invocation; combine with `--max-budget-usd` and an external timeout/SIGINT-then-SIGTERM wrapper.
- The SDK is a wrapper over the same Claude Code binary, so CLI and SDK have the same permission/sandbox semantics; choose the SDK when you need `canUseTool` callbacks, hooks as in-process functions, or typed messages.

## 2. LangGraph Deep Agents: harness features, filesystem/permissions, limits for strict isolation

### Takeaway
Deep Agents is a LangGraph-based agent harness providing a planning tool, a filesystem tool set over pluggable backends, and subagents via a `task` tool. It has declarative path-based read/write permissions, but these cover only the built-in filesystem tools and explicitly do not apply to sandbox backends or custom/MCP tools, and `FilesystemBackend` / `LocalShellBackend` give "no security" unless you add `virtual_mode` and (for shell) a real sandbox. It is not itself an isolation layer.

### Cited Findings
- Planning: `write_todos` tool via `TodoListMiddleware`; "Starting in v0.7 task planning is opt-in only." Statuses pending / in progress / completed. — [Deep Agents overview](https://docs.langchain.com/oss/python/deepagents/overview)
- Filesystem tools: `ls`, `read_file`, `write_file`, `edit_file`, `delete` (needs `deepagents>=0.7`), `glob`, `grep`; `execute` exists only with sandbox backends. — [overview](https://docs.langchain.com/oss/python/deepagents/overview)
- Subagents: built-in `task` tool, default `general-purpose` subagent, custom subagents; sync by default with async option; "Subagents are stateless and cannot send multiple messages back" (single final report). — [overview](https://docs.langchain.com/oss/python/deepagents/overview)
- Other features: skills (progressive loading), memory from `AGENTS.md`, context summarization/offload, automatic prompt caching for Anthropic and Bedrock models, `interrupt_on` for human-in-the-loop approval per tool. — [overview](https://docs.langchain.com/oss/python/deepagents/overview)
- Backends: `StateBackend` (in-memory/LangGraph state), `StoreBackend`, `FilesystemBackend` (real disk under `root_dir`), `CompositeBackend` (route by path prefix, longest prefix wins), custom backends, sandbox backends (implement `SandboxBackendProtocolV2`; named providers include LangSmith, AgentCore, Daytona) which add `execute`. — [Backends](https://docs.langchain.com/oss/python/deepagents/backends); [overview](https://docs.langchain.com/oss/python/deepagents/overview)
- `FilesystemBackend` warning: agents get "direct filesystem read/write access", can read secrets like `.env`, changes are permanent; `virtual_mode=True` with `root_dir` blocks `..`, `~` and absolute paths outside root; "the default (`virtual_mode=False`) provides no security even with `root_dir` set." `root_dir` must be absolute (quickstart examples pass `.`, a doc inconsistency). Recommended for local projects and CI, not for web servers. — [Backends](https://docs.langchain.com/oss/python/deepagents/backends)
- `LocalShellBackend`: `execute` runs `subprocess.run(shell=True)` "with no sandboxing"; commands "can access any path on the system"; `virtual_mode=True` "provides no security with shell access enabled"; defaults `timeout` 120s, `max_output_bytes` 100,000; HITL "strongly recommended". — [Backends](https://docs.langchain.com/oss/python/deepagents/backends)
- Permissions: `FilesystemPermission(operations=["read"|"write"], paths=[globs], mode="allow"|"deny"|"interrupt")`; "read" covers `ls`, `read_file`, `glob`, `grep`; "write" covers `write_file`, `edit_file`, `delete`; first matching rule wins, in declaration order; **if no rule matches the operation is allowed** (default-allow); `interrupt` mode needs `deepagents>=0.6.8`. — [Permissions](https://docs.langchain.com/oss/python/deepagents/permissions)
- Subagents inherit the parent's permissions by default; a `permissions` field in a subagent spec replaces them entirely. — [Permissions](https://docs.langchain.com/oss/python/deepagents/permissions)
- Limitation (quoted in substance): permissions apply only to built-in filesystem tools; custom tools and MCP tools touching the filesystem are not covered; they "do not apply to sandbox backends" because those can run arbitrary commands via `execute`. — [Permissions](https://docs.langchain.com/oss/python/deepagents/permissions); [overview](https://docs.langchain.com/oss/python/deepagents/overview)
- Read-only recipe in docs: `CompositeBackend` routing `/memories/` and `/policies/` to a store, plus a deny rule for `write` on those paths. Also read-only agents via a `tools` allowlist on `FilesystemMiddleware` or `excluded_tools` in a harness profile. — [Permissions](https://docs.langchain.com/oss/python/deepagents/permissions); [overview](https://docs.langchain.com/oss/python/deepagents/overview)

### Inferences
- For a factory, Deep Agents is a harness/orchestration library; the sandbox must come from elsewhere (container/bwrap around the whole Python process, or a sandbox backend). With `execute`, permission rules do nothing, so a "read-only evaluator" guarantee cannot rest on `FilesystemPermission`.
- Because of default-allow semantics, a deny list is fragile; prefer an allowlist ordering (allow specific workspace path, then a final catch-all deny rule) - an inference from "first match wins" and "no match = allowed".
- Model-agnostic: Deep Agents can drive a local OpenAI-compatible vLLM endpoint through a LangChain chat model (inference from LangChain design; the fetched pages did not demonstrate it - UNVERIFIED here).

### Gaps
- Tracing/observability: LangSmith integration for Deep Agents not fetched (the sandbox provider list mentions LangSmith); no verified statement on trace setup or self-hosted alternatives.

## 3. Single-box Linux sandboxing without root: bubblewrap, Landlock, containers, separate OS user, egress control

### Takeaway
On this exact machine, the facts that matter are: kernel 6.17 with Landlock enabled, `bwrap` 0.9.0 installed, Ubuntu AppArmor's unprivileged user-namespace restriction is ON (so plain bwrap is partially blocked and the Claude Code fix needs root), no passwordless sudo, Docker present with the user in the `docker` group (rootful Docker, effectively root-equivalent), no podman/firejail. Landlock (unprivileged, no AppArmor profile needed) and an agent-per-container-with-`:ro`-mounts are the realistic options; a second OS user needs root to create.

### Cited Findings
**Probed on the target machine (2026-10-17, my own commands, not documentation)**
- Kernel `6.17.0-1026-nvidia`; `/sys/kernel/security/lsm` = `lockdown,capability,landlock,yama,apparmor,ima,evm`; `kernel.apparmor_restrict_unprivileged_userns = 1`; `kernel.unprivileged_userns_clone = 1`; `user.max_user_namespaces = 511827`; `kernel.yama.ptrace_scope = 1`. — local probe
- `/usr/bin/bwrap` is bubblewrap 0.9.0; `/usr/bin/docker` present; `podman`, `firejail`, `socat` NOT found; `/etc/apparmor.d/` contains an `unprivileged_userns` profile but no `bwrap` profile. User `hasan-spark` (uid 1000) is in groups `sudo` and `docker`; `sudo -n true` prompts for a password. Docker runtimes: `runc` only (no gVisor `runsc`); `docker info` showed no rootless indication. — local probe
- bwrap smoke tests: `bwrap --ro-bind / / --dev /dev --proc /proc --unshare-all true` failed with `loopback: Failed RTM_NEWADDR: Operation not permitted`; `bwrap --ro-bind / / --tmpfs /tmp true` failed with `setting up uid map: Permission denied`. So bwrap as-is does not work for this user on this host; the Claude Code sandbox will likely need the AppArmor profile (root) or will fall back to unsandboxed unless `failIfUnavailable` is set. I did not run `/sandbox` in Claude Code itself to confirm. — local probe, consistent with [Sandboxing: Set up Linux](https://code.claude.com/docs/en/sandboxing)
- `socat` is also a Claude Code Linux sandbox dependency and is absent. — local probe + [Sandboxing](https://code.claude.com/docs/en/sandboxing)

**Documentation facts**
- bubblewrap is "the unprivileged sandboxing tool that enforces filesystem isolation"; on Ubuntu 24.04+ the default AppArmor policy prevents it creating user namespaces; fix is an AppArmor profile for `/usr/bin/bwrap` with `flags=(unconfined)` (root needed). Inside Docker, Claude Code's sandbox needs `enableWeakerNestedSandbox` which "considerably weakens security". — [Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Landlock: unprivileged self-restriction, stackable LSM, first in Linux 5.13; ABI v2 (REFER), v3 (TRUNCATE), v4 (TCP bind/connect port rules), v5 (device ioctl), v6 (abstract UNIX socket and signal scoping), v9 (pathname UNIX domain socket connect restriction), v10 (UDP), up to v11 on the doc page; requires `no_new_privs` for unprivileged processes; max 16 stacked rulesets. — [Landlock kernel docs](https://docs.kernel.org/userspace-api/landlock.html)
- Landlock limitations: cannot restrict mount/pivot_root topology changes; chroot not denied; files reachable via `/proc/<pid>/fd/*` or `/proc/<pid>/ns/*` can't be explicitly restricted; chdir, stat, flock, chmod, chown, setxattr, utime, fcntl, access listed as not restrictable; OverlayFS rules do not propagate between layer and merged hierarchy; before ABI v6/v9 Unix socket connections are unrestricted (relevant to reaching e.g. Docker socket). — [Landlock kernel docs](https://docs.kernel.org/userspace-api/landlock.html)
- Docker group membership: the Claude Code docs warn that access to `/var/run/docker.sock` "effectively grants access to the host system". — [Sandboxing: Security limitations](https://code.claude.com/docs/en/sandboxing)
- Container read-only mount and no-network recipe, gVisor and Firecracker options, and the same-kernel caveat are in the secure-deployment page (see Section 1). Docker's default seccomp "blocks ~44" syscalls. — [secure deployment](https://code.claude.com/docs/en/agent-sdk/secure-deployment)
- Network egress: Claude Code's built-in proxy filters by hostname without TLS inspection (domain fronting caveat); `network.strictAllowlist` / `allowManagedDomainsOnly` make the proxy refuse non-allowed hosts in every mode, including `bypassPermissions`; in bypass mode, hosts outside the allowlist are otherwise allowed. Stronger pattern: `--network none` + Unix-socket proxy outside, or an iptables default-deny (Anthropic example dev container). — [Sandboxing](https://code.claude.com/docs/en/sandboxing); [secure deployment](https://code.claude.com/docs/en/agent-sdk/secure-deployment); [sandbox environments](https://code.claude.com/docs/en/sandbox-environments)
- Anthropic's `sandbox-runtime` (bubblewrap-based on Linux) is "a beta research preview, and its configuration format may change". — [sandbox environments](https://code.claude.com/docs/en/sandbox-environments)

### Inferences
- Options ranked for this box (my assessment): (1) Docker container run by the factory user with `--cap-drop ALL --security-opt no-new-privileges --read-only --network none` etc. and `:ro` bind mounts for evaluator/labels - works without sudo because of the `docker` group, but the docker group is root-equivalent so the agent must never get the docker socket (and "rootless" is not configured). (2) A Landlock wrapper (e.g. a small launcher using the kernel API, ABI >= 4 on 6.17 is expected; exact ABI level not probed) around the whole agent process for path-level read/write denial with no AppArmor involvement. (3) bwrap, only if an admin adds the AppArmor profile. (4) A separate OS user needs root to create (not verified that one exists).
- Container with GPU access (for a local vLLM) is separate from the agent container; the agent container needs only an HTTP route to vLLM, which can be a Unix socket or a loopback-published port restricted by iptables; not tested.
- Landlock plus network ABI v4 could restrict the agent to connecting only to the vLLM port, a cheap egress control; unverified on this host.

### Gaps
- Official bubblewrap, firejail, podman (rootless prerequisites such as subuid/subgid ranges and `newuidmap`) and Docker rootless documentation were not fetched; I make no claims about escape CVEs for these beyond the vendor statements above. No specific bwrap/Landlock/firejail CVE research was done.
- Landlock ABI version actually exposed by kernel 6.17.0-1026-nvidia was not probed.
- Whether Claude Code's `/sandbox` actually fails closed on this host was not tested.
- GB10/DGX OS specifics (whether Docker has the NVIDIA runtime configured, cgroup limits for memory sharing with other model servers) not investigated.

## 5. Orchestrating several coding agents safely: worktrees, merge queues, locks, budgets, kill switches

### Takeaway
Claude Code has first-class git-worktree support (CLI `--worktree`, subagent `isolation: worktree`, hooks to replace creation) with built-in checks to stop a worktree session editing the main checkout, but worktrees isolate files only, not ports, databases, the shared `.git` directory, or arbitrary shell writes. Merge queues, file locks, and fleet-wide budgets are not documented as Claude Code features; they must be built in the orchestrator.

### Cited Findings
- `claude --worktree <name>` (`-w`) creates `.claude/worktrees/<name>/` on a new branch `worktree-<name>`; a different name starts a parallel isolated session; reusing a name reopens the worktree; `-p --worktree` skips the trust check; non-interactive runs leave worktrees (and their `git worktree lock`) in place until a later stale-lock sweep or manual `git worktree remove` / `git worktree unlock`. — [Worktrees](https://code.claude.com/docs/en/worktrees)
- Base branch: `worktree.baseRef` `"fresh"` (default, branch from remote default branch; fetch capped at 5 s, once per 24 h) or `"head"`; cannot be set to a branch name - use `git worktree add` for that. `--worktree "#1234"` branches from a PR. `.worktreeinclude` copies gitignored files (e.g. `.env`) into new worktrees. — [Worktrees](https://code.claude.com/docs/en/worktrees)
- Isolation enforcement: Claude Code blocks Edit/Write/NotebookEdit targeting the main checkout, Bash commands whose cwd resolves to the main checkout, git redirects (`git -C`, `--git-dir`, `GIT_DIR`, `GIT_WORK_TREE`), and commands whose git target cannot be verified; also applies to subagents. It does NOT track writes by `cp` or shell redirects into the main checkout - those fall to permissions/sandbox. — [Worktrees: How Claude Code enforces isolation](https://code.claude.com/docs/en/worktrees)
- Shared between worktrees: the repository `.git` directory (sandbox allows these writes so `git commit` works), project-scope plugins, and "Yes, don't ask again" permission approvals saved to the main checkout's `.claude/settings.local.json`. — [Worktrees](https://code.claude.com/docs/en/worktrees)
- Subagent worktrees: `isolation: worktree` frontmatter; temporary worktree removed if no changes; one with changes stays until a sweep older than `cleanupPeriodDays`; Claude Code holds a `git worktree lock` while an agent runs. Hook `${CLAUDE_PROJECT_DIR}` does not follow the worktree; use `cwd` in hook input. Hooks `WorktreeCreate` / `WorktreeRemove` can replace the default git logic. — [Worktrees](https://code.claude.com/docs/en/worktrees); [hooks](https://code.claude.com/docs/en/hooks)
- Worktree creation skips repo-defined git filter drivers (a security measure since "anything that can write to the repository, including Claude, could have put one there"); Git LFS local installs yield pointer files. Creation is refused if `.claude` / `.claude/worktrees` is a symlink. — [Worktrees: Troubleshooting](https://code.claude.com/docs/en/worktrees)
- Other parallelism features exist: subagents, "agent teams", cross-session messaging, background agents (`agent-view`), `/batch` - pages referenced but not read. — [Worktrees: See also](https://code.claude.com/docs/en/worktrees)
- Budgets/kill: `--max-budget-usd` / `maxBudgetUsd` per call; `--max-turns` (flag exists per headless/CLI docs; not shown on the fetched headless page, UNVERIFIED here); SIGINT (graceful end of turn) vs SIGTERM (exit 143, process-tree kill, SessionEnd hook runs); SDK `interrupt()`. — [headless](https://code.claude.com/docs/en/headless); [cost tracking](https://code.claude.com/docs/en/agent-sdk/cost-tracking)
- Deep Agents `interrupt_on` and `FilesystemPermission` mode `interrupt` give human approval gates; `LocalShellBackend` has `timeout` 120 s default. — [Permissions](https://docs.langchain.com/oss/python/deepagents/permissions); [Backends](https://docs.langchain.com/oss/python/deepagents/backends)

### Inferences
- A merge queue is the factory's job: agents commit to `worktree-<ticket>` branches; a single serial integrator (one process, no agent) rebases, runs the evaluator in a read-only/separate environment, and fast-forwards `main`; this avoids concurrent writes to shared files. Git itself already serializes ref updates with lock files, but semantic conflicts need the queue (general git knowledge, not from fetched sources).
- Locks on shared files (lockfiles, generated files, shared datasets) belong in a PreToolUse hook that consults a lock service or `flock` file, exiting 2 on conflict (hook mechanics are documented; the lock pattern is my proposal).
- Per-ticket budget: set `--max-budget-usd`, a wall-clock timeout (SIGINT, then SIGTERM after grace), a max-turns cap, and a global kill switch (a flag file checked by a PreToolUse hook with `onFailure:"block"`, plus the orchestrator killing the process group). Fleet-wide spend must be summed by the orchestrator from each run's `total_cost_usd` (client-side estimate only).
- With one local GPU server shared by several local-model agents, concurrency is bounded by vLLM throughput and the other model servers' memory; queue tickets rather than running many agents (a design inference; no measured data).
- Worktrees plus a sandbox that allows write only to that ticket's worktree and its `.git` entries (`allowWrite`) gives per-ticket blast-radius; the shared `.git` directory remains writable by every agent, so one agent could in principle rewrite refs/hooks (`.git/hooks` is write-protected by sandbox-runtime and "protected paths" per docs; whether every agent can still rewrite branch refs of other tickets is an inference, not tested).

### Gaps
- No documented merge-queue, lock-service, or fleet-budget feature for Claude Code or Deep Agents was found; the patterns above are inferences, not sourced practice. I did not search community write-ups on multi-agent worktree orchestration (e.g. open-source orchestrators) or GitHub merge queue docs.
- `agent-teams`, `agents`, `sub-agents` (including subagent depth/concurrency/spend limits) pages were not fetched.
- No data on resource contention (disk, ports, GPU memory) across parallel worktrees on a single machine.
- Deep Agents/LangGraph worktree patterns: none found.
